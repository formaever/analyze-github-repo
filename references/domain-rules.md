# 仓库分析规则

## 适用范围与来源

用于解释软件仓库的功能与实现，不用于证明生产环境正常或业务效果有效。

这些规则是本案例的内部分析规范，不是行业认证或第三方标准。外部协议、平台限制或业务数据必须另附实际来源、适用版本和日期。

## 能力声明分类

对每项主要功能使用以下分类，可同时成立：

1. 有实现证据：能定位到执行相应功能的代码或配置，并解释其输入输出。
2. 有运行证据：观察到相应执行记录和结果，注明环境、输入及覆盖范围。
3. 仅有声明：只在说明文档、注释或提示词中出现，尚未找到执行证据。
4. 依赖外部能力：由宿主、第三方服务或仓库未包含的组件完成。
5. 未知：当前材料不足以判断。

有代码不等于已运行成功，单次成功不等于覆盖所有情况。配置和自然语言指令可以构成系统的一部分，但不能据此推断约束必然被执行。

## 分析 Skill 时的特殊规则

- “必须搜索”是执行要求，不是已发生的工具调用。
- 角色设定、提示词提炼不等于训练、微调或复制真人。
- 多 Agent 分工指令不等于仓库自带调度引擎。
- 参考资料目录不等于存在向量索引、Embedding 或检索服务。
- 脚本通过只能证明代码实际检查的条件成立。
- 示例回答、截图或模型评分不能直接证明业务效果。
- 检查生成、调用、更新三个阶段，不把创建流程误当成每次调用流程。

## 证据要求

- 重要实现判断附文件路径和行号，或固定版本源码链接。
- 同一条结论的证据尽量来自同一版本；引用行号必须对应实际读取内容。
- 只检查了部分范围时写“在已检查范围内未发现”，不要直接断言不存在。
- 必要时追踪被调用函数，不能只依据函数名、接口名或注释判断实现。
- 区分仓库自带功能、可选集成、示例特有功能与未来计划。
- 作者声称运行成功而未独立复测时，写成“仓库报告”，不要写成自己的验证结果。
- 对外引用不得泄露令牌、密码或用户未授权公开的私有内容。

## 引用检查与语义复核

`check_evidence.py` 只检查字段、文件和行号，不对 `claim` 做语义判断。

位置检查通过后，仍需回答：

1. 引用是否直接支持结论，而不只是出现相关名称？
2. 是否遗漏了影响结论的分支、调用、配置或异常行为？
3. 是对单个函数的局部观察，还是足以推广到整个项目？
4. 结论描述的是实际实现，还是文档要求、研究推断或运行假设？

## 正反示例

不合格：项目实现了全面的事实核验。

合格：脚本检查引用文件和行号是否有效，但没有验证结论是否被引用内容支持。

不合格：说明文档写了支持多 Agent，因此项目自带调度引擎。

合格：指令要求宿主启动子 Agent；独立调度实现仍需寻找代码证据。

不合格：函数名是 check_limitations，因此它会逐个检查所有模型的局限。

合格：函数只在全文搜索相关关键词，未遍历各个模型，不能证明每个模型都包含局限。

不合格：评分为 96/100，因此有 96% 的真人还原率。

合格：这是特定量表下的评分；其题目、评委、样本规模和运行链路覆盖需要分别核查。

## 信息不足与矛盾

- 访问失败：指出缺失文件及其影响，不补写想象中的实现。
- 文档与代码冲突：分别引用，并以实际代码解释已观察行为。
- 未运行：只报告静态分析结论，明确运行表现未知。
- 测试覆盖有限：描述已覆盖输入，不推断未覆盖情况。
- 来源或版本冲突：保留差异，先核查日期、提交和适用范围。

## 交付验收

- 功能描述与实际证据范围相符。
- 典型流程包含输入、处理、外部依赖和输出。
- 关键结论有来源，引用位置与被分析版本一致。
- 推断和未知内容可辨认。
- 不把静态格式检查等同于语义验证或功能测试。
